# Поиск объявлений услуг: описание решения

Решение объединяет словный и смысловой поиск, географию и историю выбора объявлений. CatBoost отбирает итоговые 50 кандидатов. Ниже описаны устройство поиска, подготовка признаков и ограничения локальной проверки.

## Задача и данные

Для каждого запроса нужно вернуть до 50 объявлений из заданного корпуса. Качество оценивается по Recall@50, усреднённому по запросам. Для каждого запроса знаменатель включает все известные положительные объявления, в том числе не найденные среди кандидатов. Порядок внутри ответа не влияет на результат, важен состав выбранных объявлений.

Исходный train содержит 497 673 пары запроса и выбранного объявления и 344 825 разных объявлений. [Первичный профиль](../data_dump/reports/data_profile.json) насчитывает 73 873 текста запросов после простой нормализации: нижний регистр, замена `ё` на `е`, выравнивание пробелов. Итоговый поисковый нормализатор дополнительно использует NFKC и регулярное выражение, поэтому даёт 73 706 разных текстов. Различие подтверждено [независимым пересчётом](independent_audit.json). Корпус benchmark содержит 189 212 объявлений. В файле запросов 2 452 строки. Положительные пары известны только для train. Отсутствие пары в train само по себе не доказывает, что объявление не подходит.

Используются текст запроса и его фильтры, заголовок, описание и параметры объявления, статистики подкатегорий, локация и координаты. Цена, рейтинг, число отзывов и доступные способы связи служат дополнительными признаками для отбора кандидатов. Идентификаторы объявлений нужны для связывания таблиц и формирования ответа. Идентификатор запроса и буквальное совпадение категории запроса с категорией объявления не используются итоговыми моделями.

По первичному профилю с простой нормализацией 37,36% текстов benchmark встречались в train, а полный контекст запроса встречался в 4,40% случаев. Контекст состоит из нормализованного текста, локации, флага доставки, фильтров и категории. Только 9,59% объявлений корпуса встречались в обучающих парах. Последнее число описывает весь корпус: доля знакомых объявлений среди скрытых правильных ответов неизвестна и может заметно отличаться.

Исходные данные остаются локальными. Публичное описание содержит агрегаты и устройство алгоритма, без фрагментов пользовательских записей.

## Откуда берутся кандидаты

Решение объединяет несколько источников, поскольку один способ поиска может пропустить подходящее объявление. Каждый источник возвращает свою группу кандидатов, после чего повторы удаляются.

**Поиск по словам.** Тексты приводятся к нижнему регистру, `ё` заменяется на `е`, русские слова обрабатываются [SnowballStemmer из NLTK](https://www.nltk.org/api/nltk.stem.snowball.html). Числа и латиница сохраняются: они нужны для моделей техники, марок и размеров. Словный TF-IDF использует отдельные слова и пары соседних слов в заголовках и параметрах. Отдельный канал учитывает фильтры запроса. [Описание TF-IDF в scikit-learn](https://scikit-learn.org/stable/modules/feature_extraction.html#tf-idf-term-weighting).

**BM25.** Поиск также использует описание объявления. Заголовок повторяется трижды, параметры дважды, чтобы длинный рекламный текст меньше вытеснял основную услугу. Описание ограничено первыми 3 000 символами. Реализация использует положительный IDF и насыщение частоты слова, параметры `k1=1.2`, `b=0.65`. [Формулы и параметры BM25 в Lucene](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html).

**Символьный поиск.** TF-IDF по фрагментам длиной 3–5 символов дополняет словный поиск при близких написаниях и опечатках. Отдельного эксперимента, изолирующего только его вклад, в итоговом сравнении нет.

**Смысловой поиск.** Используется открытая модель `intfloat/multilingual-e5-small`, ревизия `614241f622f53c4eeff9890bdc4f31cfecc418b3`. Запросы получают префикс `query:`, объявления получают `passage:`. Векторы усредняются по токенам без заполнителей и нормализуются, как рекомендовано в [официальной карточке E5](https://huggingface.co/intfloat/multilingual-e5-small). Размерность вектора равна 384. Для нормализованных векторов скалярное произведение равно косинусной близости.

Каждый запрос кодируется двумя способами: текст вместе с фильтрами и только текст. Объявление представлено заголовком, параметрами и первыми 2 000 символами описания в таком порядке. Порядок полей выбран в этом решении, а не задан моделью. Вход ограничен 256 токенами для объявления и 128 для запроса. Сохранённые эмбеддинги рассчитаны на Apple MPS в `float32`, пакетами по 64 текста. Оба представления запроса используют один и тот же индекс объявлений. Ревизия и контрольные суммы файлов модели записаны локально.

**История выбора.** Отдельный индекс ищет похожие обучающие запросы по словам и символам. Их известные выборы дают кандидатов и распределение подкатегорий. Кроме этого, считаются частоты выбора объявления, пары «текст и объявление» и полного контекста с объявлением. Для нового объявления эти счётчики равны нулю, но распределение его подкатегории можно оценить по похожим запросам. Все такие статистики строятся только по доступной обучающей части.

Лимиты источников заданы до объединения и удаления повторов:

| Источник | Глобально | С географической поправкой |
| --- | ---: | ---: |
| Словный TF-IDF | 100 | 220 |
| BM25 | 100 | 500 |
| Символьный TF-IDF | 100 | 350 |
| TF-IDF запроса вместе с фильтром | не используется | 220 |
| Обучающие выборы похожих запросов | 60 | 120 |
| E5: запрос вместе с фильтром | 120 | 300 |
| E5: только текст запроса | 120 | 300 |

Географические словные каналы расширены после анализа пропусков на dev. Их лимиты не означают такое же число новых уникальных объявлений: источники пересекаются. Отрицательная косинусная близость сама по себе не исключает кандидата E5. Если объединение содержит меньше 50 объявлений, запасной источник использует число отзывов с географической поправкой.

## География и фильтры

Точное совпадение локаций встречается в 83,10% положительных обучающих пар. При этом у 17,41% запросов benchmark вообще нет объявлений с тем же идентификатором локации в корпусе. Поэтому жёсткое ограничение одним идентификатором заведомо теряет часть ответов.

Для локаций объявлений рассчитывается медиана координат. Если локация запроса не встречается у объявлений, её центр оценивается по обучающим переходам в известные локации. Признаки включают совпадение идентификаторов, логарифм расстояния, наличие координат, вероятность перехода и отношение этой вероятности к общей частоте локации объявления. Расстояние остаётся мягким признаком: координаты бывают неточными, а некоторые услуги оказываются удалённо.

Ширина поиска оценивается взвешенной медианой расстояний до выбранных локаций. При ширине больше 300 км географический штраф ослабляется. Такой поиск нельзя привязывать к одному крупному городу только потому, что он оказался центром наблюдений. Для остальных запросов соседние локации получают плавно убывающий вес, а переходы из train помогают учитывать региональный охват. Правила для конкретных идентификаторов локаций не задаются.

Дополнительно считается доля обучающих выборов внутри той же локации для каждой подкатегории, со сглаживанием к общей доле. Признак `category_local_rate` описывает подкатегорию объявления, а `query_local_rate` усредняет такие доли по распределению подкатегорий похожих запросов. Они помогают модели отличать преимущественно местные услуги от услуг с более широким охватом.

Поиск выполняется глобально и с географической поправкой. Для словных оценок применяется плавный множитель, для близости E5 используется логарифмическая поправка. В общий набор попадают оба типа кандидатов, поэтому география не становится обязательным фильтром.

Фильтры также не превращаются в обязательные ограничения. Среди 320 264 обучающих пар с распознанным видом услуги соответствующий текст найден в параметрах объявления в 98,36% случаев. Остаются несовпадения, а многие широкие виды услуг охватывают десятки подкатегорий. Поэтому соответствие фильтра подкатегории и покрытие слов фильтра используются как признаки вместе с размером обучающей поддержки.

Признак `category_match` исключён из всех финальных моделей. В train категория поиска `0` встречается лишь в 34 строках из 497 673, в benchmark код указан в 222 запросах из 2 452. У объявлений корпуса категории `0` вообще нет, а все 34 известных положительных примера такого поиска относятся к категории `114`. Буквальное сравнение даёт ноль для каждого кандидата этих 222 запросов, хотя почти все обучающие положительные пары имеют совпадающую категорию. Чтобы не переносить этот сдвиг на модель и не предполагать точное значение кода `0`, поле оставлено только для диагностики и убрано из обучения через `--drop-features category_match`. Факты и решение сохранены в [reports/category_shift.json](../data_dump/reports/category_shift.json).

## Отбор 50 объявлений

Для объединённого набора считаются оценки и позиции каждого источника, географические и поведенческие признаки, покрытие заголовком слов запроса и дополнительные характеристики объявления. Признак `full_coverage` показывает долю разных стем-токенов запроса, найденных в индексируемом тексте объявления: заголовке, параметрах и первых 3 000 символах описания. Для него используется бинарное присутствие термов в матрице BM25, поэтому повторы слов не увеличивают покрытие. Простая исходная схема объединяет нормированные текстовые оценки с географической близостью.

Итоговый отбор использует `CatBoostClassifier` с функцией потерь `Logloss`. Известная положительная пара получает метку 1, остальные сгенерированные кандидаты получают 0. Участие запроса в fit, dev или audit определяется до обучения. Число деревьев выбирается по macro Recall@50 на dev, а не по значению Logloss. Классификатор обучается на отдельных парах, без групповой функции потерь. При ранжировании используются его исходные оценки `RawFormulaVal`. [Документация CatBoostClassifier](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier).

Выбран равновесный ансамбль двух моделей глубины 6: первая содержит 700 деревьев и использует прямые признаки истории объявления, вторая содержит 1 000 деревьев и исключает шесть таких признаков: `popularity`, `memory_score`, `text_item_count`, `context_item_count`, `rank_memory`, `rank_geo_memory`. Название `no_history` относится только к этому исключению. Статистики похожих запросов, подкатегорий, фильтров и географии остаются, а обе модели используют общее объединение кандидатов, включающее поведенческие источники.

У обеих моделей `Logloss`, скорость обучения 0,07 и seed 42. Их оценки стандартизуются внутри каждого запроса и складываются с весами 0,5 и 0,5. Конфигурация заморожена до просмотра качества audit в [configs/selection.json](../data_dump/configs/selection.json). Финальное обучение выполняется на 4 500 запросах fit и dev с выбранным числом деревьев. Audit не входит в обучение и используется однократно, без последующего изменения зафиксированной конфигурации.

Номер строки в корпусе и признак попадания объявления в добавленную часть локального корпуса не передаются модели. Нельзя позволить ей отличать проверочные объявления по способу сборки данных.

## Локальная проверка и её ограничения

Разделение фиксируется с seed `20260928`. Отобраны 6 000 контекстов с 6 432 положительными парами: 3 000 запросов для обучения отбора, 1 500 для выбора параметров и 1 500 для итоговой проверки. В выборке есть знакомые контексты с частью скрытых объявлений, новые контексты знакомых текстов и полностью новые тексты.

Все проверяемые пары «контекст и объявление» удаляются из обучающих переходов. Для новых текстов удаляются все их обучающие строки. Также скрывается история случайно выбранных 90,4% целевых объявлений. Последняя доля задана как допущение стресс-теста. Доля среди скрытых правильных ответов benchmark неизвестна. После совместного применения ограничений в 96,56% положительных проверочных пар целевое объявление не встречается в оставшейся обучающей истории. Доля знакомых составляет 3,44%. Знакомые тексты составляют 36,97% запросов, доля знакомых контекстов равна 4,37%.

Поиск выполняется по всему исходному корпусу benchmark и 5 913 добавленным отложенным объявлениям, всего по 195 125 документам. Случайная маленькая подвыборка негативов не используется. Описания отложенных объявлений доступны поисковым индексам, как и при настоящем поиске по корпусу, а факты их выбора скрыты от обучающих статистик. При проверке сохранённых файлов пересечения со скрытыми парами и новыми текстами не обнаружены. Повторная сборка с тем же seed дала побайтно одинаковые корпус, обучающие переходы, запросы и разметку. Контрольные суммы приведены в [reports/split_reproducibility.json](../data_dump/reports/split_reproducibility.json).

Идентификаторы, контексты и нормализованные тексты запросов fit, dev и audit попарно не пересекаются. По объявлениям разделение не полностью раздельное: между fit+dev и audit есть 22 общих целевых `item_id`. В дополнительной проверке после фиксации модели исключены 22 audit-запроса, содержащие хотя бы одно такое объявление. На оставшихся 1 478 запросах и 1 573 положительных парах Recall@50 равен 0,941249436175, оценка с прежними весами по доле пустых фильтров равна 0,942929047334. Обучение и выбор модели не повторялись. Срез устраняет пересечение известных целевых объявлений, но сохраняет общий корпус кандидатов. Полностью раздельного по объявлениям эксперимента он не заменяет. [Результаты независимой проверки](independent_audit.json) и [пояснение](independent_audit.md).

Для ответа на benchmark статистики взаимодействий строятся заново по всему исходному train. Кандидаты ограничиваются 189 212 объявлениями исходного benchmark, добавленные для локальной проверки объявления в ответ не допускаются.

Такая проверка сложнее задачи только в некоторых отношениях. Корпус немного больше исходного, разметка неполная, доля новых целевых объявлений задана искусственно. Поэтому локальный результат нельзя считать обещанием результата на платформе. Помимо общего Recall@50, нужно отдельно смотреть новые и знакомые целевые объявления, запросы с фильтрами и без них, географию и полноту объединённого набора до отбора 50.

У benchmark пустые фильтры встречаются в 63,05% запросов. В локальной проверке их 45,62%, в исходном train 32,95%. Дополнительная оценка с поправкой на этот сдвиг равна `0.6305057 × Recall(без фильтров) + 0.3694943 × Recall(с фильтрами)`. Веса рассчитаны по открытым признакам benchmark, без его разметки. Такая оценка дополняет обычную метрику, но не устраняет другие различия распределений.

Длинное описание может быть обрезано, а длинные параметры способны вытеснить его из входа E5. Короткий или неоднозначный запрос иногда не содержит достаточно сведений о выбранной услуге. Неполная разметка также означает, что среди кандидатов с меткой 0 могут быть подходящие объявления. Эти ограничения сохраняются после объединения источников и обучения отбора.

На 1 500 запросах dev до финального переобучения на fit и dev получены следующие значения:

| Вариант | Recall@50 |
| --- | ---: |
| Глубина 6, 700 деревьев, с прямыми признаками истории | 0,942611 |
| Глубина 6, 1 000 деревьев, без шести прямых признаков истории | 0,939167 |
| Равновесный ансамбль после стандартизации оценок | 0,942944 |

Для выбранного ансамбля оценка с весами по наличию фильтров составляет 0,937137. Конфигурации глубины 7 и проверенные смеси с ними не улучшили результат. Отчёты сравнения сохранены в [reports/hybrid_models_dev.json](../data_dump/reports/hybrid_models_dev.json) и [reports/history_ablation_dev.json](../data_dump/reports/history_ablation_dev.json).

Прибавка ансамбля относительно первой модели равна всего 0,000333. Парный bootstrap по запросам, 2 000 повторов с seed 42, даёт 95-процентный интервал разницы от −0,004333 до 0,005000. Интервал включает ноль, поэтому статистически подтверждённого превосходства нет. Ансамбль выбран по лучшему наблюдаемому dev Recall, а ослабление зависимости от прямой истории при неизвестной доле новых объявлений остаётся дополнительным соображением, не доказанной гарантией. Эти результаты использованы при выборе модели и не заменяют независимую проверку на audit.

## Воспроизводимость

Минимальный [ноутбук](../mini/solution.ipynb) заново применяет сохранённые модели к числовым признакам benchmark. Исходные тексты и веса E5 для этого запуска не нужны. Полная подготовка признаков и обучение описаны в [исходном решении](../reference_solution/README.md). Следующие команды относятся к нему.

Ноутбук проверен отдельно в чистой папке с новым ядром и пустым `PYTHONPATH`. Готового `answer.csv` перед запуском не было. Все 5 ячеек с кодом выполнены за 5,949 секунды, полученный CSV побайтно совпал с основным ответом. Проверены 2 452 строки и ровно 50 кандидатов на запрос. [notebook_verification.json](notebook_verification.json) содержит контрольные суммы входов и результата, число выполненных ячеек и условия запуска. Проверка подтверждает применение сохранённых моделей, без повторного обучения и пересчёта E5.

Исходный архив загружается отдельным скриптом `scripts/download_data.py`. Можно передать готовый архив через `--archive` и выполнить подготовку без сети. Архив проверяется по SHA256 `8dd3cba59201bae333c11db89c5111198fa10cc52a70c70bdc57bd6a248fb777`, затем извлекаются только три ожидаемых Parquet-файла. При установленном PyArrow проверяются числа строк.

Модель E5 также подготавливается отдельной явной командой. После подготовки данных и весов вычисление признаков, обучение и получение ответа выполняются локально, без внешних API. Для эмбеддингов сохраняются контрольные суммы исходника, модели и порядок идентификаторов. Нельзя переиспользовать кэш для другого корпуса или переставленных строк. Версии библиотек зафиксированы в `pyproject.toml`.

Скрипт `scripts/reproduce.py` поддерживает сохранение ответа из готовых артефактов и полный пересчёт через `--rebuild`. Во втором случае он заново готовит split, индексы, эмбеддинги и признаки, затем обучает модели с фиксированными параметрами и формирует ответ. Смена CPU на MPS или обратно может дать небольшие численные различия в эмбеддингах. Побайтное совпадение результата после такого переноса отдельно не подтверждено, поэтому сохранённые параметры устройства и точности существенны для воспроизведения.

В ответ записываются исходные строковые `query_id` и `item_id`. Проверяются полнота запросов, отсутствие повторов, принадлежность объявлений корпусу, ограничение 50 и ровно две колонки CSV. Решение не содержит правил для конкретных `query_id` и не пытается вручную восстановить скрытые ответы.

В отдельной проверке исходного архива после распаковки заново получены все три ответа: `answer.csv`, `answer_with_history.csv` и `answer_no_history.csv`. Все SHA256 совпали с сохранёнными ответами, в каждом файле проверены 2 452 запроса и ровно 50 кандидатов. Подтверждение содержится в [verification.json](../data_dump/verification.json), поля `reproductions[*].passed` и `all_regenerated_outputs_match`. Проверка использовала готовые числовые признаки и модели. Полный пересчёт E5 и повторное обучение в эту проверку не входили.
